# Browser-Native Capture Numerical Acceptance and Evidence Matrix

Status: **frozen numerical-acceptance contract for Photivra engine issue #233,
deliverable 2**.

This document defines which #224 browser-first dense-pupil capture results are
exact contracts, which are tolerance-governed numerical quantities, which require
refinement/convergence evidence, and which must fail closed.

It complements
[Browser-First Dense-Pupil Native Capture Qualification Envelope](BROWSER_NATIVE_CAPTURE_ENVELOPE.md)
and the
[Browser-Native Capture Prepared-State, Ownership, and Invalidation Contract](BROWSER_NATIVE_CAPTURE_PREPARED_STATE.md).
The envelope owns supported source/camera/stage scope; the prepared-state contract owns reuse/invalidation semantics; this document owns numerical acceptance and evidence classification.

It does not implement a backend, change equations, loosen existing tests, or
claim that a full-native case currently passes.

## Governing rules

The repository-wide [Numerical Correctness](NUMERICAL_CORRECTNESS.md) policy
remains authoritative:

- exact identity remains exact;
- integer/raster/seed/output identities are not tolerance-governed;
- floating-point integration/interpolation/inverse calculations use documented
  quantity-specific acceptance;
- a looser tolerance may not be introduced merely to hide a regression;
- independent analytical/reference values are preferred to implementation-to-
  implementation agreement;
- convergence/refinement evidence is required where sampled numerical methods
  own the error;
- a pure implementation optimization must preserve scientific meaning and
  provenance.

The [Scientific Assurance](SCIENTIFIC_ASSURANCE.md) contract remains authoritative
for model/source/calibration uncertainty. Numerical tolerance in this document
must never be reported as total physical uncertainty.

## Error domains must remain separate

The qualification evidence must distinguish these error/uncertainty domains.

1. **Physical-model applicability** — whether the declared source/camera model is
   valid for the requested case.
2. **Source/calibration uncertainty** — uncertainty in evidence-backed source,
   optical, or sensor data.
3. **Deterministic numerical error** — finite-precision arithmetic, interpolation,
   quadrature, reduction order, and conditioned inverse/intersection calculations.
4. **Stochastic integration uncertainty** — only if a separately versioned Path-B
   stochastic estimator is later adopted.
5. **Physical sensor randomness** — shot/read noise generated by the existing
   seeded sensor model.
6. **Quantization** — explicit clipping/rounding/ADC code behavior.

An implementation may not hide numerical integration variance inside the physical
sensor-noise distribution. Noise-free expected photon/electron quantities are
qualified before the stochastic sensor/noise/ADC stages.

## Acceptance classes

Every evidence row below uses one of these classes.

### X — exact semantic identity

The value or state must compare exactly. No epsilon is allowed.

Examples: IDs, versions, native indices, CFA channel assignments, sample counts,
seed schedules, work counters, task state, serialized discriminants.

### R — exact authoritative RAW/output identity

Every required integer RAW code and code-associated exact metadata must match the
reference result exactly for the declared deterministic fixture and seed.

A floating-point implementation difference is not permission to tolerate a
different RAW code.

### N — tolerance-governed numerical quantity

The quantity is inherently floating-point/numerical. Acceptance must use an
explicit criterion tied to that quantity and fixture.

Where this matrix cites an existing repository threshold, that threshold is a
**regression floor for that constructed test**, not a universal real-camera
accuracy statement.

### C — convergence/refinement evidence

The claim is accepted only with a defined sequence of refinements and observed
stability/error behavior. Agreement between two implementations at one sampling
level is insufficient.

### S — statistical evidence

Reserved for a separately approved stochastic numerical method. It requires
multiple independent scrambles/seeds and a predeclared estimator/statistical
criterion. It is not used by Path A.

### F — fail-closed safety behavior

Malformed, unsupported, canceled, resource-exceeding, or precision-ambiguous input
must not yield an authoritative partial capture.

## Precision policy

### Float64 reference

The compact Path-A reference defined by #234 uses binary64 arithmetic for its
scientific floating-point reference calculations, matching JavaScript Number and
any explicitly qualified WebAssembly `f64` implementation.

WebAssembly Core 3.0 defines `f32` and `f64` floating-point values corresponding
to the respective IEEE-754 binary formats:

https://webassembly.github.io/spec/core/syntax/values.html

A WebAssembly implementation is not automatically trusted merely because it uses
`f64`; it must still pass the same evidence matrix.

### WebGPU/WGSL candidates

The W3C WGSL Candidate Recommendation Draft current during this review
(21 September 2026) defines concrete runtime `f32` and optional `f16` shader
types. `AbstractFloat` uses binary64 representability for shader creation-time
expression evaluation, but it is not a concrete runtime `f64` shader type.

https://www.w3.org/TR/WGSL/

Therefore:

- no WebGPU backend may claim float64-equivalent runtime precision from WGSL
  literal/abstract evaluation;
- GPU geometry and accumulation require independent BNCE-GEO/BACKEND evidence;
- higher-precision CPU accumulation cannot repair a GPU ray that selected the
  wrong visible surface;
- unsupported/ambiguous precision cases use BNCE-FALLBACK-001 rather than a silent
  scientific downgrade.

These platform facts must be reverified if #235 is implemented against a later
WGSL/WebGPU specification.

## Exact RAW and floating-point intermediates

The numerical contract intentionally distinguishes floating-point intermediates
from authoritative integer outputs.

A backend may differ from the float64 reference within an approved N-class
criterion for an intermediate expected photon/electron quantity. It does **not**
receive a corresponding ±1-code allowance for BNCE-RAW-001.

For deterministic acceptance fixtures:

1. qualify the noise-free expected signal first;
2. apply the existing physical sensor/noise/ADC stages with the established seed
   schedule and ordering;
3. compare required integer RAW codes exactly.

If a tolerance-governed intermediate difference changes a required deterministic
RAW code, that backend does not satisfy Path-A equivalence for that case. It must
fall back, reject, or enter a separately reviewed numerical-method/version change.

This rule deliberately protects full-well/clipping/ADC-threshold cases.

## Numerical tolerance governance

This matrix freezes acceptance **type** and existing regression floors. It does
not invent physical error bars.

A new numeric tolerance is accepted only when the owning PR records:

- the quantity and unit;
- absolute versus relative form;
- expected magnitude/range;
- numerical conditioning and algorithm;
- independent analytical/reference construction;
- why the tolerance is tighter than any material downstream threshold or scientific
  claim it could affect;
- test cases immediately inside and outside the accepted bound;
- whether the criterion is backend-independent or backend-specific.

If those facts are unavailable, the criterion remains unresolved and the affected
backend/case remains unqualified.

## Convergence/refinement governance

For BNCE-REF-PUPIL-001, BNCE-REF-TIME-001, and any later C-class criterion:

- one coarse/fine pair alone is not a universal convergence proof;
- the comparison quantity must be named explicitly;
- discontinuous visibility cases require shifted/sliver/edge controls rather than
  assuming smooth asymptotic convergence;
- a refinement that exceeds the admitted work/resource contract is evidence of a
  blocker, not permission to raise the limit;
- if Path A cannot establish the required envelope, that obstruction may trigger
  #236 after its method-specific contract is reviewed.

## Reproducibility record

Every executed qualification evidence record must include at least:

- BNCE evidence ID(s);
- source/fixture identity and hash/version;
- engine commit;
- algorithm/integrator/prepared-state version when applicable;
- backend and precision identity;
- raster and all spatial/temporal/pupil/spectral sample counts;
- capture/source/profile IDs and relevant seed;
- chunk/batch configuration;
- measured work counters;
- pass/fail/unsupported outcome;
- independent reference/oracle identity;
- acceptance criterion used;
- for performance/resource evidence, device/runtime identity and measurement
  conditions.

Performance measurements do not substitute for numerical acceptance.
