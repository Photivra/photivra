# WebGPU devices: hardware record

The devices on which the `webgpu-f32` backend ([WebGPU backend](WEBGPU.md)) has been checked, one row per run. A row records what the run's report and the issue it was posted to state, and nothing else; a cell says "not recorded" where the run did not capture that fact. Add a row for every hardware run of `npm run test:webgpu:hardware` (conformance: accuracy against the float64 reference, within the bounds of [docs/WEBGPU.md](WEBGPU.md#accuracy-contract)) or `npm run bench:webgpu:hardware` (timings at 6–24 MP; the run prints one summary line per frame and stage with the GPU and CPU milliseconds and their ratio, so a row copies them). The steps are in [Running on hardware](WEBGPU.md#running-on-hardware).

A release's record links the rows of this table whose engine commit is in that release; a bound of `docs/WEBGPU.md` is confirmed only on the devices whose conformance row passed. A software adapter (SwiftShader, the CI job `webgpu conformance (SwiftShader)` in [`.github/workflows/webgpu.yml`](../.github/workflows/webgpu.yml)) checks the kernels' arithmetic, not a GPU; it is not a hardware row.

Reading the rows:

- The two October 27 runs are the same machine; the Mac model, chip, memory and browser version were given in follow-up comments on #277 (the bench run's own report has "version not captured" for the browser).
- Of the stages timed on October 26 and 27, the convolution, temporal sum, SDR, luminance and RAW-development stages met their bounds on this device (the conformance row), so their timings stand as GPU timings of conformant kernels. The sensor stage's 7–9× does not count as a confirmed result until #471 is fixed and the conformance suite passes on this device.
- The ratios compare the GPU with one CPU thread of the float64 reference in the same browser. They are the stages' own cost, not a capture's.
- The two later October 27 rows are the pre-fix baseline of the composite probe finding (docs/RELEASE_2_11_0.md, Known issues): every composite and `material-layers` test was refused by the probe, everything else passed. Their timings are informational (one run, 1024 × 768). The re-run on the commit with the fix goes in a new row, with the probe's class and product path that the harness now prints per case.

## Adding a row

1. Run the suite or the bench as [Running on hardware](WEBGPU.md#running-on-hardware) describes; with `PHOTIVRA_WEBGPU_TIMING_OUT`, save the bench's JSON report under `docs/validation/webgpu-devices/` named by date and device.
2. Copy into the row: the device (model, chip, memory), the adapter line the report prints (`vendor` / `architecture`, `softwareAdapter`), the GPU driver version if the OS shows it, the browser and its version, the OS and its version, the engine commit hash, the suite that ran and the date, the result (passed/total for the conformance suite with the failing tests named; the summary lines for the bench) and the timings file.
3. Post the same facts in the issue that tracks the work, and link the row from the release record of the version that first ships the engine commit.
